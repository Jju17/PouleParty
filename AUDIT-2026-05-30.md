# PouleParty Pre-Launch Security & Quality Audit

**Audit date:** 2026-05-30 · **D-Day:** 2026-06-06 (7 days out) · **Lead auditor report**

---

## 1. Executive Summary

### Overall health

PouleParty is, on the whole, a **mature and well-engineered cross-platform codebase**. The hardest parts — server-authoritative game-state transitions, the deterministic zone-math determinism layer (splitmix64 PRNG bit-identical across Swift/Kotlin/TS), the Stripe payment/webhook core, the power-up collect/activate atomicity, and win detection — are in genuinely good shape, and several previously-critical findings from prior audits (CRIT-2, CRIT-3, CRIT-10, CRIT-11, PP-40) have been verifiably closed. The Cloud Functions layer is hardened with transactional CAS flips, deterministic Cloud Task dedup, signature-verified idempotent webhooks, and constant-time secret compares.

That said, **there are no confirmed Critical findings, but there is one High finding with direct compliance/revenue stakes for the paid D-Day event** (paid-event join gating absent from clients and rules), plus a cluster of High parity/localization gaps that will be visible to French and Dutch players on day one.

### Launch-readiness verdict

**Conditional GO.** No finding is a hard blocker to the core game mechanic working, and the payment intake itself is solid. However, three classes of issue should be resolved or consciously accepted before D-Day:

1. **The paid-event access model is undecided in code.** Either paid gating regressed, or the docs are stale. This must be a deliberate decision, not an accident (see HIGH-1).
2. **FR/NL players will see English and even French-hardcoded strings** on launch-critical screens (manual launch overlay, GameMaster designation dialog). For a Belgium-first, FR-primary audience this is a visible quality regression (HIGH-4, HIGH-5).
3. **Several server-side trust boundaries are looser than the UI** (chicken designation, RTDB validation, foundCode relocation window). None are slam-dunk exploits given anonymous auth + UI constraints, but #2 below (RTDB) and the foundCode window are worth tightening.

### Top 5 risks before D-Day

| # | Risk | Severity | Why it matters for D-Day |
|---|------|----------|--------------------------|
| 1 | **Paid-event games joinable with only the 6-char gameCode** — validation-code gate absent from both clients and `firestore.rules` | High | The D-Day event is paid (12€/player). Anyone who learns the code can join without paying, unless this was an intentional move to wristband-only validation. **Decision required.** |
| 2 | **FR/NL localization gaps on launch screens** — 19 untranslated iOS keys + Android GameMaster dialog hardcoded in **French** | High | FR-primary audience sees English/wrong-language strings on the manual-launch overlay and chicken-designation dialog the moment the game starts. |
| 3 | **PP-72 proximity anti-cheat does not exist at runtime** | High | Challenges can be validated from anywhere; the only gate is a human eyeballing the photo. Documented anti-cheat is fiction. |
| 4 | **RTDB rules lack status/start-time gating + coordinate validation** | High/Med | Chicken position readable during waiting/head-start window; coordinates spoofable. Privacy + integrity enforced client-side only. |
| 5 | **Live zone radius diverges from server recap** (integer truncation + inconsistent collapse boundary) | Medium | The zone the players actually play can be larger/longer-lived than the creation preview, and can shrink past the 50m final disc, causing wrongful out-of-zone penalties. |

#### HIGH-1 · PP-52 validation-code gate absent from both clients and `firestore.rules`: paid-event games joinable with only the gameCode
- **✅ RESOLVED 2026-05-31** — Reintroduced a single-use registration-code gate (manual entry, no deeplink, Apple 3.1.1-conscious). Games with `Game.registrationBatchId` now require the unique code from the registration email, validated + single-use-claimed server-side by the `validateRegistrationCode` callable (1 paid registration = 1 join). iOS + Android + functions, all tests green; not yet deployed. See `[[project_pp52_code_gate]]`. (`maxPlayers` = exact paid headcount remains the secondary cap.)
- **Axis:** Join flow & registrations (PP-90) · **Platforms:** iOS, Android, rules · **Verdict:** confirmed
- **Location:** `ios/PouleParty/Features/JoinFlow/JoinFlow.swift:12-22` & `:143-146`; `android/.../ui/home/HomeViewModel.kt:478-482`; `firestore.rules:53-63` (hunterIds update) & `:151-156` (registrations create)
- **What's wrong:** CLAUDE.md and both rule docs describe a required `validationCodeEntry` step (checked via `validateRegistrationCode` against a paid `eventRegistration`) for batch-linked games. In code, neither `Step`/`JoinFlowStep` enum has that case, neither `joinAsHunterTapped` branches on `registrationBatchId`, and `firestore.rules` has zero batch/paid checks on either the join or registrations-create rules. Net effect: any authenticated user who learns the 6-char gameCode can join the paid D-Day event without paying. This may be intentional (the rules comment says "PP-90 dropped the in-app registration-required gate"), but it leaves paid events ungated via the normal gameCode path.
- **Fix:** Make a deliberate decision and align all three layers. If paid gating is still required, reintroduce the `codeValidated → validationCodeEntry → joiningWithTeamName` step on both clients and add a callable join gate (rules can't query `eventRegistrations`). If gating is genuinely deprecated, update CLAUDE.md + both rule docs. **This intersects with the deeplink/wristband compliance walk-back (MED-7, MED-9) — resolve them together.**

#### HIGH-2 · PP-72 proximity anti-cheat is completely absent at runtime
- **Axis:** Challenges, validation & leaderboard · **Platforms:** functions, iOS, Android · **Verdict:** [uncertain]
- **Location:** `functions/src/validation.ts:43-155` (no distance check); `ios/.../Features/Challenges/Challenges.swift:267-297`; `android/.../ui/challenges/ChallengesViewModel.kt:168-207`; models `Challenge.swift:18` / `Challenge.kt:24`
- **What's wrong:** `proximityRadiusMeters` and `challenge.location` are decoded into the model on both platforms but never read by any submission path. The hunter flow (tap "Doing it" → camera → upload → submission doc) does no distance computation, and `validateChallengeSubmission` never loads location/radius either. If it's intentionally advisory-only, stop calling it anti-cheat in the docs.

#### HIGH-3 · Chicken-designation rule accepts any non-empty string as `chickenId` and lets the GM mutate `hunterIds` arbitrarily in the same write
- **Axis:** GameMaster role · **Platforms:** rules · **Verdict:** confirmed
- **Location:** `firestore.rules:93-101`
- **What's wrong:** The PP-86 re-designation rule (creator OR any GM, while `status=='waiting'`) validates only that `chickenId` is a non-empty string not present in the new `hunterIds`. It does **not** verify the new `chickenId` was actually a hunter, and it permits `hunterIds` to be edited in the same write with no caller-only / delta constraint (unlike the precise join rule at 53-63). A buggy/malicious GM client can orphan the chicken role onto a non-participant UID and simultaneously remove arbitrary hunters. The UI is safe; rules are the real trust boundary and are looser.
- **Fix:** Require `resource.data.hunterIds.hasAny([request.resource.data.chickenId])` and constrain the `hunterIds` delta to exactly removing that UID. Better: move designation behind a callable that reads `/registrations` and enforces candidate validity server-side.

### 🟡 Medium

#### MED-1 · `processRadiusUpdate` integer-truncates the decline, diverging the live radius from the server `circles[]` schedule and collapse boundary
- **✅ OBSOLETE 2026-06-04** — Neutralized by PP-zone-stored (landed after this audit). The runtime reads the server-generated `/games/{id}/zone/schedule` (`circles[index].radiusMeters`, exact Double floored identically per device) on all three maps; `processRadiusUpdate` / `findLastUpdate` have ZERO runtime callers (verified: tests + comments + reference-mirror only on both platforms). The recap renders the same CF `circles[]`. No per-device Int-truncation divergence possible. Same root cause as LOW-PARITY-1, also obsolete.
- **Axis:** Zone mechanics · **Platforms:** iOS, Android, functions · **Verdict:** confirmed
- **Location:** `ios GameTimerLogic.swift:308` / `android GameTimerHelper.kt:332` vs `functions/src/zoneCalculation.ts:288-304`
- **What's wrong:** Live timer shrinks as `Int(radiusDeclinePerUpdate)` / `.toInt()` (truncates toward zero), e.g. 145.8 → 145 m/step, while the server subtracts the full float. Over 10+ shrinks the schedules diverge by metres-to-tens-of-metres and hit collapse at different step counts; the live zone is larger/longer-lived than the creation recap predicted. Both clients truncate identically so the two players stay in sync, but neither matches the server-authoritative recap or the power-up center math.
- **Fix:** Use identical rounding on all three: round the decline once (`Math.round`) when persisting `shrinkMetersPerUpdate` so it's integral, or carry radius as float on clients and round only for display. Add a parity golden walking N shrinks asserting identical radius sequence AND collapse step index.

#### MED-2 · Zone-collapse boundary uses three inconsistent thresholds (`>0` live vs `<=50` schedule vs `<=0` drift), so the live zone shrinks past the final disc
- **✅ OBSOLETE 2026-06-04** — Neutralized by PP-zone-stored. `computeShrinkSchedule` clamps the last circle to `max(FINAL_ZONE_RADIUS=50, …)` so the stored schedule never goes below 50 m; the runtime reads `circles[index].radiusMeters` (floored at 50) and the out-of-zone evaluator uses that same active circle (`HunterMap.swift:1027 zoneRadius: circle.radius`). The `>0`/`<=0` "zone has collapsed" thresholds live only in `processRadiusUpdate` (no runtime callers). Game-over fires by time / all-found / cancel, not radius collapse. No sub-50 window, no wrongful penalty.
- **Axis:** Zone mechanics · **Platforms:** iOS, Android, functions · **Verdict:** confirmed
- **Location:** `ios GameTimerLogic.swift:310` / `android GameTimerHelper.kt:333` vs `zoneCalculation.ts:289` vs `GameTimerLogic.swift:199` / `GameTimerHelper.kt:222`
- **What's wrong:** Live timer ends only when integer radius `<= 0`; server recap clamps to the 50m final disc (`FINAL_ZONE_RADIUS=50`); drift collapses disk B once `newRadius <= 51`. The recap promises a 50m final disc, but the live timer keeps shrinking through 50…1m, and in that sub-50 window the final-zone glow no longer fits inside the drifted circle — **players standing in the 50m glow can be outside the live circle and take an out-of-zone penalty**, violating the "every circle contains the final zone" invariant.
- **Fix:** Make the live timer stop/clamp at `FINAL_ZONE_RADIUS` (50m), not 0. Restores the invariant and aligns live game ↔ recap ↔ out-of-zone evaluator.

#### MED-3 · Live `stayInTheZone` center uses `deterministicDriftCenter` only, while the spawner composes `interpolateZoneCenter` THEN drift — zone center and power-up spawn center diverge
- **✅ OBSOLETE 2026-06-04** — Neutralized by PP-zone-stored. Both paths now read the SAME pre-computed stored schedule: `spawnBatchForGame` reads `circles[effectiveBatchIndex].lat/lng` as the spawn center (`index.ts:497-527`), and the runtime maps render `circles[index].center` via `zoneRenderStateFromCircles`. The drift/interpolate composition is baked into the schedule once at creation. The client `deterministicDriftCenter` / `interpolateZoneCenter` calls survive only in `processRadiusUpdate` + the recap-preview reference (no runtime callers). Center divergence is impossible by construction.
- **Axis:** Zone mechanics · **Platforms:** iOS, Android, functions · **Verdict:** [uncertain]
- **Location:** `ios GameTimerLogic.swift:330-336` / `android GameTimerHelper.kt:346-359` vs `functions/src/powerUpSpawn.ts:51-70`
- **What's wrong:** The drawn circle center is pure `deterministicDriftCenter(basePoint=initialCenter,…)` (no `interpolateZoneCenter`), while the server spawner computes `interpolateZoneCenter(initial→final by progress)` then drift. These are different points (drift samples a disc; interpolate returns the exact lerp). Power-ups can spawn measurably off-center from the visible circle, worst case near/outside the edge.
- **Fix:** Pick one composition for both paths. Either drop `interpolateZoneCenter` from the spawn path, or apply it to the live circle's basePoint before drift. Add a parity test asserting live circle center == power-up batch center for the same `(seed, shrink step)`.

#### MED-4 · `zoneFreeze` spawn-batch adjustment is single-step only — a 120s freeze across a <2min shrink interval (incl. the 1-min debug default) desyncs spawn radius from the rendered zone
- **✅ FIXED 2026-06-04 (option B)** — Ported the client `selectActiveCircle` freeze-aware index walk to TS (`selectActiveCircleIndex` in `zoneCalculation.ts`) and replaced the fixed `batchIndex - 1` in `spawnBatchForGame` with it, so the spawner counts EVERY shrink tick inside the freeze window (not just one) and picks the exact circle the clients render. Server-only (clients were already correct). 5 unit tests pin the 2-boundary case. Built + tests green; not yet deployed.
- **Axis:** Power-ups · **Platforms:** functions · **Verdict:** [uncertain]
- **Location:** `functions/src/index.ts:480-526`
- **What's wrong:** With a `zoneFreeze` active, `effectiveBatchIndex = batchIndex - 1`; the code comment admits it "Doesn't handle multiple historical freezes perfectly." `zoneFreeze` lasts 120s. With a creator-tunable (or QA-debug-default) 1-min shrink interval, a single freeze spans **two** shrink boundaries; each batch subtracts only 1, so batch N+1's radius is wrong and power-ups land outside the rendered circle.
- **Fix:** Count shrink boundaries elapsed during the active freeze window instead of a fixed `-1`, OR enforce `shrinkIntervalMinutes*60 > max freeze duration`. Verify iOS/Android `findLastUpdate` apply the identical freeze adjustment.

#### MED-5 · `hunterLocations` write rule does not enforce `chickenCanSeeHunters` / GM-joined broadcast gating
- **Axis:** Location tracking (PP-102) · **Platforms:** rules · **Verdict:** [uncertain]
- **Location:** `database.rules.json:20`
- **What's wrong:** The write rule checks identity + key presence but not `chickenCanSeeHunters` or non-empty `gameMasterIds`. In `stayInTheZone` with no GM there should be no hunter position sharing, but a tampered client can persist GPS and the chicken can read it — privacy enforced client-side only.

#### MED-6 · No `.validate` constraints on any RTDB location/presence node — coordinates, timestamp, presence and invisible flag are shape/range-spoofable
- **Axis:** Location tracking (PP-102) · **Platforms:** rules · **Verdict:** [uncertain]
- **Location:** `database.rules.json:11-28` (all leaf nodes)
- **What's wrong:** Every write rule uses only `newData.hasChildren([...])`. A client can write out-of-range lat/lng, non-numeric/future `ts`, extra children, or forge/omit the `invisible` flag. PP-87 invisibility is enforced for hunter *reads*, but malformed payloads can desync map rendering or clock logic on consumers.
- **Fix:** Add `.validate` per leaf: `lat`/`lng` numeric + range, `ts` numeric, `invisible` boolean when present, `$other: {".validate": false}` to reject extra keys; validate `presence` `online`/`ts` types. (Overlaps with LOW security findings on the same nodes.)

#### MED-7 · meta-mirror propagation lag creates a join / launch / chicken-swap authorization race
- **Axis:** Location tracking (PP-102) · **Platforms:** rules, functions · **Verdict:** confirmed
- **Location:** `functions/src/rtdbMirror.ts:53-79` + `database.rules.json` (all conditions read `meta`)
- **What's wrong:** All RTDB auth derives from `meta`, populated asynchronously by the `onDocumentWritten` trigger after the Firestore commit. During the gap (cold start = seconds): a just-joined hunter is denied location writes/reads; a swapped chicken's old UID briefly retains write access. Symptom: a few seconds of blank map / inability to broadcast right after joining or launching.
- **Fix:** Write the meta mirror inline (admin SDK) inside the join / `launchGame` / chicken-swap callables in addition to the trigger. Ensure clients retry RTDB reads/writes with backoff (confirm the "3-attempt retry" covers RTDB). Keep the trigger as catch-all.

#### MED-8 · `applyOutOfZonePenalty` is non-idempotent: every call subtracts 1, no dedup token, no floor — a client retry double-penalizes
- **Axis:** Challenges/validation + Cloud Functions · **Platforms:** functions · **Verdict:** confirmed (lifecycle axis) / [uncertain] (challenges axis) — **same defect, dual-reported**
- **Location:** `functions/src/validation.ts:168-212`
- **What's wrong:** The penalty callable computes `next = existingTotal - 1` with no penalty-event id, no quantized-interval guard, no `Math.max` floor. The clients wrap callables in `withRetry` (3 attempts); a transient error after server commit retries and double-penalizes. `totalPoints` can go arbitrarily negative; a malicious hunter can drive it down at will, and the leaderboard faithfully propagates the corruption.
- **Fix:** Persist a `lastPenaltyAt` per hunter and reject calls inside `outOfZonePenaltyInterval` server-side (ideally move out-of-zone detection fully server-side using RTDB position + zone math). At minimum pass a `penaltyEventId`, store applied ids, and clamp at a floor.

#### MED-17 · `foundCode` relocation to `/private` is best-effort; failure leaves the code permanently readable on the public game doc
- **Axis:** Security rules / Cloud Functions · **Platforms:** functions, rules · **Verdict:** confirmed
- **Location:** `functions/src/index.ts:904-921` (relocation), `firestore.rules:8` (game doc read: if signed-in)
- **What's wrong:** `onGameCreated` copies `foundCode` to `/private/security` then blanks the public field — **after** the client created the doc, so there's a window where the public, all-signed-in-readable doc still carries the real code. ## 4. Security Posture Summary

The rules are **single shared files** (no platform divergence) and, after line-by-line review against the backing Cloud Functions, are **substantially stronger than a quick read suggests**. The corrected, confirmed posture:

### What is solid (confirmed)
- **Win detection is fully server-authoritative:** no client `winners`-update rule (denied by default, `firestore.rules:65-69`); `submitFoundCode` reads the secret from `/private/security`, constant-time compares, idempotent via `alreadyWinner` guard.
- **Hunter join rule** is strictly `hasOnly(['hunterIds'])` with set-diff caller-only enforcement and a `maxPlayers` cap (`:56`) — no `winners`/`gameMasterIds`/`powerUps` escalation, no over-capacity.
- **Power-up collection boundary** is the rule's `collectedBy==null` precondition (`:229-233`), not the client transaction (INFO-4) — no double-collect/steal. **Power-up creation is `if false`** (admin-SDK only).
- **`activatePowerUp`** derives the `activeEffects` key from the validated `pu.type` (no client field-path injection) and checks `collectedBy===uid` + `!activatedAt`.
- **Locked collections:** `/private`, `/challenges` (template), `/eventRegistrations` (`:298-300`), `/aggregates` (`write:false`), `gmRateLimits`, `validationRateLimits`, `accountDeletionRequests`.
- **RTDB `meta` is read=write=false** (clients can't read the roster; rules read it via `root.child` which bypasses the node's own `.read`); the chicken-read rule correctly enforces `gameMode=='followTheChicken' && invisible!=true` for hunters, so **PP-87 invisibility is server-enforced for hunter reads** and stayInTheZone hunters can't read the chicken at all.
- **Stripe webhook:** signature-verified, idempotent transactional `paid` flip with amount/currency/mode cross-checks; refund full-vs-partial split with `refunded==true` guard.

### Where the rules are looser than they should be (actionable before D-Day)
| Finding | Severity | One-liner |
|---|---|---|
| HIGH-1 | High | Paid-event join has **no** batch/paid gate at the rules layer |
| HIGH-3 | High | Chicken-designation rule accepts any string as `chickenId` + lets GM edit `hunterIds` freely |
| MED-6 / LOW-21 | Med/Low | **No RTDB `.validate`** — coordinates/ts/invisible spoofable |
